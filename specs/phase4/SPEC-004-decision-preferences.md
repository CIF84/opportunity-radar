# SPEC-004 — Versioned Decision Preferences and Bounded Preference Effects

`IMPLEMENTED_AWAITING_APPROVAL`

## Purpose

Implement the next bounded Phase 4 slice: a separately fingerprinted, taxonomy-backed, time-varying decision-preference layer that adjusts opportunity ranking without contaminating capability evidence or semantic-v1 identity.

This packet deliberately separates:

- what the candidate can do;
- what the job requires;
- what the candidate currently prefers;
- how a preference stance maps to a numeric ranking effect;

## Product principle

Preferences are not permanent personality facts.

They are versioned, inspectable, candidate-controlled decision policy that may change over time.

Future product interactions may generate evidence about changing sentiment, for example:

- reordering opportunities in a ranked feed;
- promoting/demoting opportunities;
- APPLY / REVIEW / DONT_APPLY decisions;
- annotations such as "interesting role, wrong industry";
- repeated preference for one role characteristic over another.

Those observations must **not** silently rewrite authoritative preferences.

The governed learning loop remains:

```text
interaction / judgment
  -> observation
  -> repeated pattern
  -> preference hypothesis
  -> explicit promotion / accepted update
  -> new preference version
```

No autonomous preference learning is implemented in this packet.

## Preference state vocabulary

Use the durable ordinal vocabulary:

```text
STRONG_POSITIVE
POSITIVE
NEUTRAL
NEGATIVE
```

Semantics:

### STRONG_POSITIVE

A material reason to pursue an otherwise plausible opportunity and a meaningful reason to rank it above similar alternatives.

Observed examples / initial candidate concepts include:

- AI / automation transformation;
- meaningful transformation execution;
- implementation ownership / execution authority.

### POSITIVE

A meaningful but weaker attraction that should improve relative ranking among otherwise comparable opportunities.

Observed examples / initial candidate concepts include:

- commercial/business operations;
- product development / product strategy;
- substantial learning upside;
- strategic optionality where represented by the existing taxonomy.

### NEUTRAL

No material candidate preference effect.

Omitted preferences are equivalent to neutral and must not create a hidden positive or negative effect.

### NEGATIVE

A meaningful aversion that lowers relative attractiveness but is **never a hidden veto**.

Observed initial candidate concepts include:

- customer-service operations;
- pure advisory consulting without implementation ownership;
- orthopaedics;
- legacy advertising/agency economics;
- social-influencer operations;
- low employer/product/sector conviction where explicitly configured.

Do not introduce `STRONG_NEGATIVE` in this first experiment.

If something is truly unacceptable, it belongs in an explicit hard constraint/market/eligibility policy rather than being disguised as a preference.

## Preference state versus scoring policy

These are separate contracts.

Conceptually:

```text
DecisionPreference
- concept_id
- stance
- optional rationale
- optional effective_from / version evidence if consistent with current config model

PreferenceEffectPolicy
- policy_id / version
- stance_to_effect mapping
- aggregate lower/upper bounds
```

A preference can remain `POSITIVE` while a later experiment changes the mapping from `POSITIVE -> +0.2` to another value.

Changing the numeric effect policy must not rewrite historical preference state.

Changing candidate preference state must not invalidate semantic assessments.

## Initial bounded effect mapping

Freeze the following initial experimental mapping before retrospective replay:

```text
STRONG_POSITIVE -> +0.4
POSITIVE        -> +0.2
NEUTRAL         ->  0.0
NEGATIVE        -> -0.3
```

Aggregate preference effect is bounded to:

```text
[-1.0, +1.0]
```

on the existing 0–10 opportunity score scale.

This mapping is **an experimental decision policy, not a claim about psychological truth**.

The purpose is to allow preferences to materially reorder opportunities and occasionally cross an existing recommendation boundary without overwhelming capability/fit evidence.

Do not tune these numbers against the frozen 30-case batch in this packet.

## Aggregation rules

Preference effects must be deterministic, inspectable, and non-duplicative.

Requirements:

- match governed concepts, not arbitrary keywords where avoidable;
- each configured preference concept contributes at most once per opportunity unless the taxonomy explicitly models distinct dimensions;
- aggregate raw effect is the sum of matched concept effects;
- final effect is clipped to `[-1.0, +1.0]`;
- preserve both raw and clipped values for auditability;
- preserve the matched concepts, stance, effect, and evidence source;
- omitted/unmatched preference concepts contribute zero.

Do not double-count the same semantic evidence through synonyms/aliases that resolve to one concept.

## Preference concept modeling

Use reusable taxonomy/configuration rather than one-off branches.

The initial candidate preference vocabulary should represent at least the observed categories necessary for the frozen Live Validation cases, including where supported by current taxonomy/configuration:

- AI / automation;
- transformation execution;
- implementation ownership / execution authority;
- commercial/business operations;
- product development / strategy;
- learning/growth upside;
- customer-service operations;
- advisory-only consulting;
- orthopaedics;
- legacy advertising/agency sector;
- social-influencer operations.

Do not create broad negative concepts when the observed preference is narrow.

Example:

```text
orthopaedics -> NEGATIVE
```

must not become:

```text
healthcare -> NEGATIVE
```

because the candidate explicitly found other biology/technology intersections attractive.

Likewise:

```text
advisory_without_implementation_ownership -> NEGATIVE
implementation_ownership -> STRONG_POSITIVE
```

is preferred to:

```text
consulting -> NEGATIVE
```

The WPP evidence is an important trade-off regression:

```text
legacy agency             NEGATIVE
AI / automation           STRONG_POSITIVE
implementation ownership  STRONG_POSITIVE (where evidenced)
learning upside            POSITIVE
```

must remain capable of producing a net positive preference effect and must not be vetoed solely by the negative industry preference.

## Conviction versus preference

Preserve the conceptual distinction between subjective attraction and contextual market/employer/product conviction.

For the first implementation, both may feed the same bounded decision-effect arithmetic **only if** their source/type remains explicit in structured evidence.

Prefer a reusable type field or concept namespace such as:

```text
PREFERENCE
CONVICTION
```

or the closest existing architecture-compatible representation.

Examples:

- `implementation_ownership = STRONG_POSITIVE` is a candidate preference;
- `legacy_agency_sector = NEGATIVE` may represent a candidate market conviction.

Do not collapse provenance such that a future UI cannot explain the difference.

Do not build external employer-intelligence automation in this packet.

- portability fixture/test profile receives its own coherent values sufficient to prove portability, not copied primary-specific branches;

## Decision-score contract

Conceptually:

```text

+ bounded_preference_effect
= decision_adjusted_score
```

Clamp the final adjusted score to the existing score domain if necessary.

Persist/report both values separately.

Do not overwrite or reinterpret the existing stored base composite.

Do not change the six semantic dimensions or their weights.

## Recommendation composition

Use the existing deterministic recommendation thresholds against the decision-adjusted score only where Phase 4 SPEC currently intends the preference-aware decision layer to operate.

Then preserve already implemented policy precedence/caps:

- `OUT_OF_SCOPE` -> excluded;
- hard `INELIGIBLE` -> `INELIGIBLE`;
- market `UNCERTAIN` -> maximum `REVIEW`;
- explicit junior/graduate guard (when later/now applicable according to current implementation status) -> maximum `LOW_PRIORITY`;
- missing semantic dimension -> existing safe behavior;
- preference effect can change rank/recommendation within those outer policy bounds;
- a negative preference alone never creates hard `INELIGIBLE`/`OUT_OF_SCOPE`.

If the junior guard remains unimplemented in the current tree, do not implement it accidentally here unless required solely by the existing accepted Phase 4 slice numbering. Report it as next work if still pending.

## Structured preference-effect evidence

Expose a deterministic structure conceptually containing:

```text
PreferenceEffect
- concept_id
- source_type: PREFERENCE | CONVICTION
- stance
- numeric_effect
- evidence / matched job concept

PreferenceAssessment
- matched_effects
- raw_total_effect
- bounded_total_effect
- base_composite_score
- decision_adjusted_score
- decision_preference_fingerprint
```

Use codebase conventions rather than these exact names if appropriate.

This structure must be sufficient for a future feed/control panel to display *why* an opportunity moved in rank.

## Time-varying preference memory

Do not implement a temporal database/history engine now.

- preference configuration is explicitly versioned;
- historical experiment/batch artifacts preserve the preference/policy fingerprints they used;
- future profile versions may revise stances without rewriting old experiment evidence.

## Live Validation regression expectations

Do not run the full retrospective replay yet, but add focused deterministic regression tests using representative frozen evidence where feasible.

At minimum demonstrate:

1. WPP Automation & AI:
   - negative legacy-agency preference does not veto the opportunity;
   - strong AI/automation upside can outweigh it.

2. Advisory consulting case:
   - advisory without implementation ownership receives a negative effect;
   - transformation execution / implementation ownership can receive positive or strong-positive effects.

3. Orthopaedics:
   - orthopaedics receives negative effect;
   - unrelated healthcare/biology role does not inherit that aversion merely by broad sector association.

4. Customer service:
   - customer-service operations receives negative effect;
   - commercial/business operations does not.

5. Omitted preference:
   - contributes zero.

6. Multiple positive/negative effects:
   - sum deterministically;
   - clip at aggregate bound;
   - preserve raw and bounded totals.

Do not tune the mapping based on whether these cases reproduce every historical human decision. That belongs to the retrospective experiment.

## Implementation result

Implemented in the current worktree without a SQLite migration, retrospective
batch replay, live source calls, or external semantic calls. Both candidate
profiles now use one versioned decision-preference schema. Matching rules and
the frozen numeric effect policy are separate declarative configurations.
Preference assessment preserves the Phase 3 base composite, emits structured
matched evidence and bounded effect arithmetic, and adjusts ranking and
recommendation only after preferred-variant selection. Market and hard-
eligibility policy precedence remains authoritative.

Preference-only changes preserve the exact semantic-v1 and scoring-preference
fingerprints, reuse existing semantic assessments, and leave cluster identity,
member lifecycle, and SQLite schema version 3 unchanged. Focused regression
tests cover WPP AI/agency trade-offs, advisory versus implementation ownership,
narrow orthopaedics aversion, customer-service versus business operations,
neutral omissions, clipping, and synonym non-duplication. Retrospective Live
Validation replay remains the next experiment and must use an immutable new
artifact rather than modifying v1 evidence.
